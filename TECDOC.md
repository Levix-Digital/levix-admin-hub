# levix-admin-hub — Technical Documentation

Entry point to the architecture of levix-admin-hub. This index is maintained with the
`architecture-docs` skill: the sections between `architecture-docs` markers are
generated by `build_index.py`; the rest is written by hand.

## System Overview

The Admin Hub is a Rust service that a customer hosts in its own VPC or on-premises to govern
Levix product installations: organizations, users and groups, devices, licenses, policies,
approvals, break-glass passwords, metadata-only audit and the update mirror. It never sees
content ([ADR-0004](docs/adr/0004-always-hosted-by-the-customer-zero-knowledge-no-call-home.md)).

```
 Admin (browser) ──► web console ─┐
 Admin (terminal) ─► CLI ─────────┤                      ┌─► storage (SQLite | PostgreSQL)
 IdP ──────────────► SCIM ────────┼─► hub-core (use cases, ├─► bus (in-process | Redis)
 ITSM ─────────────► webhooks ────┤   ports, modules)     ├─► IdP / ITSM / mirror store
 Devices ──────────► WebSocket ───┘                      └─► key custody
 (outbound only, signed messages)
```

A request enters through a driving adapter (REST, SCIM, webhooks, the device WebSocket
channel, the web console or the CLI), becomes one use case of `hub-core`, and reaches
infrastructure only through ports
([ADR-0001](docs/adr/0001-hexagonal-architecture-with-a-modular-core.md)). State lives in one
database: SQLite in the compact profile, PostgreSQL in the scalable one
([ADR-0003](docs/adr/0003-one-codebase-two-installation-profiles-sqlite-and-in-process.md)).
Devices keep an outbound-only channel; every message the Hub sends them is signed by the Hub
key that they pinned at enrollment. The policy model, signatures and formats come from
`levix-platform`
([ADR-0005](docs/adr/0005-shared-policy-model-signatures-and-formats-from-levix-platfo.md)),
and the contract is public and versioned
([ADR-0006](docs/adr/0006-public-versioned-contract-for-the-api-and-the-device-channel.md)).

## Contract

The public contract lives in [docs/contracts/](docs/contracts/CHANGELOG.md): the REST API as
OpenAPI generated from the handlers ([openapi.json](docs/contracts/api/openapi.json), also
served at `/api/v1/openapi.json`), the device channel as AsyncAPI with JSON Schemas
([channel v1](docs/contracts/channel/v1/README.md)) and the
[permission matrix](docs/contracts/permissions.md). Tests fail when the committed document
differs from the code or an example breaks its schema; CI refuses a breaking API change within
one major contract version.

## CLI

`levix-hub-cli` (crate `hub-cli`) administers a Hub over the public API only: it depends on no
Hub crate, so it can do exactly what the API allows. Every API operation has one command, and a
test compares that table with the committed OpenAPI document. The CLI trusts the Hub through
the system certificate authorities, a CA file, or the SHA-256 fingerprint that `levix-hub init`
prints; it keeps the session token in a file readable by the user only, and a personal API
token in `LEVIX_HUB_TOKEN` replaces the session for scripts. `--output json` prints the API's
JSON, and exit codes are stable (3 not signed in, 4 not allowed, 5 not found, 6 conflict,
7 invalid input, 8 throttled, 9 unreachable or untrusted Hub, 10 Hub error).

## How to Update This Documentation

- **A subsystem changed** (behavior, structure, data): edit its page in `docs/architecture/` in place, replacing outdated text.
- **A decision with alternatives and trade-offs**: create an ADR with `new_adr.py` and link it from the subsystem page.
- **A decision that reverses or corrects another**: create a new ADR with `--supersedes` or `--amends`; never rewrite an accepted ADR.
- **A feature was removed**: remove it from the subsystem page; its ADRs stay as history.
- **A release**: nothing here; release notes live in the GitHub releases.
- Run `check_docs.py` before committing.
